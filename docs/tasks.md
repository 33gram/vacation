**Версия документа:** 2.30

**Основание:** `requirements.md` v1.23 (функциональные/нефункциональные требования), `plan.md` v1.21 (архитектура, стек, этапы M0–M8), `ui.md` v1.5 (оболочка, типы экранов, состояния, форматы, формы, тема — по прототипу M1)
**Статус:** Финальный артефакт SDD-цепочки (`requirements.md` → `plan.md` → `tasks.md`) — готов к исполнению разработчиками/AI-агентами.

**Как читать этот документ:**
- Задачи сгруппированы по этапам **M0–M8** из раздела 12 `plan.md`, внутри этапа — по слоям (модель данных → бизнес-логика/сервисы → API → frontend → тесты).
- Формат ID: `T-M{этап}-{номер}`. Порядок внутри этапа в основном последовательный; задачи с пометкой **[P]** можно выполнять параллельно с соседними (не имеют взаимных зависимостей).
- Каждая задача ссылается на функциональное/нефункциональное требование (`FR-XXX`/`NFR-XXX`) из `requirements.md` и на раздел `plan.md`, чтобы приёмка задачи проверялась напрямую по критериям EARS исходного требования.
- Задачи вида «Написать тесты на …» подразумевают покрытие **каждого** `WHEN/IF/WHILE/WHERE`-критерия соответствующего FR отдельным тест-кейсом (TDD-подход: тест пишется до или вместе с реализацией).
- Пути к файлам — согласно структуре репозитория, `plan.md` §3.
- Обозначения в тексте задач: «Разблокирует …» — какие задачи не начать, пока не сделана эта; «Унаследовано из …» — критерий вынесен из закрытой задачи в эту; «Реализует также критерий …» — эта задача выполняет критерий другой, закрытой задачи, который та сама не выносила; «ОТМЕНЕНА, не выполняется: …» — задача заведена по ошибке или потеряла смысл и не будет выполняться; чек-бокс у неё остаётся `[ ]` (она не выполнена, а отменена, `[x]` значило бы обратное), а причина отмены записывается в самом тексте задачи — чтобы она не выглядела ни забытой, ни сделанной.

Сетка на уровне приложения, симметрично обработчику `IntegrityError`/`ImportFileError` в `main.py`; отрицательный контроль обязателен. Обнаружено при ревью PR #140, третий круг. `NFR-SEC-004`.

- [ ] **T-M7-11** Заменить кириллический блок `backend/app/modules/auth/common_passwords.txt` (79 самостоятельно собранных записей, без измерения — см. шапку файла) на источник с измеренной статистикой встречаемости русских паролей, отложено с `T-M1-39` (`requirements.md` раздел 13, п. 28) до этого, предэксплуатационного этапа — решение о происхождении и лицензии корпуса, производного из утечек, принимается перед вводом в эксплуатацию, не на этапе разработки. Критерии приёмки источника: происхождение и лицензия, допускающая использование в этом репозитории; способ измерения частоты встречаемости (не общеизвестные представления, как в текущем блоке); порог отсечения — сколько записей берётся и по какому критерию (абсолютная частота, перцентиль и т. п.); размер файла и цена загрузки в множество при импорте модуля (`_load_common_passwords`, `password_policy.py`) — список читается с диска один раз при старте, но растущий порог не бесплатен; и обязательство зафиксировать в шапке файла после замены источник, коммит/версию, дату загрузки и применённый порог — так же прямо, как уже сделано для блока SecLists. Если подходящий источник не найдётся, задача закрывается явным решением «оставить эвристику» (с обоснованием, по образцу `T-M1-39`), а не молчанием. `FR-AUTH-002`.
- [ ] **T-M7-12** Прод-образ backend ставит ТОЛЬКО runtime-зависимости: отдельный хэшированный замок, генерируемый той же make-целью, что и `backend/requirements.lock` (`T-M1-55`), но без `--extra dev`. Критерий приёмки проверяется замером (`pip list` в прод-образе, собранном через `infra/docker-compose.prod.yml` (`T-M7-10`), не содержит `pytest`/`ruff`/прочих dev-only пакетов), а не чтением `Dockerfile`. Зависит от `T-M7-10` (прод-профиля, где этот замок применяется) — реализуется вместе с ним или сразу после. Происхождение долга: при выполнении `T-M1-55` переход `backend/Dockerfile`'s install-шага зависимостей с `-c constraints.txt` на `-r requirements.lock` сделал `ARG INSTALL_DEV` фактически недейственным — обе ветки ставят ОДИН И ТОТ ЖЕ замок (`--extra dev`) целиком; измерено: 62 дистрибутива в замке, 52 в runtime-замыкании без `--extra dev`, 10 только из dev (certifi, httpcore, httpx, iniconfig, pluggy, pygments, pytest, pytest-asyncio, ruff, sniffio). Выделена отдельной задачей, а не критерием внутри `T-M7-10` (PR #171 review, второй круг — пересмотр первой редакции того же ревью): объём сопоставим с `T-M1-55` самой — второй хэшированный замок, развод по точке установки прод-образа, проверка состава замером — не одна строка критерия в чужой задаче, прецедент — `T-M1-36`/`T-M1-37`, выделенные из `T-M1-11`/`T-M1-12` тем же образом.

**Готовность этапа:** пройдены все NFR из раздела 9 требований, есть подтверждённая процедура резервного копирования и восстановления.
