#
# T-M1-55: плоский список версий backend-зависимостей (прямых и
# транзитивных, runtime и dev) С ХЭШАМИ дистрибутивов, закрепляющий не
# только версию, но и конкретный артефакт — подменённый на зеркале файл
# той же версии ставился бы молча при простом закреплении версии
# (`T-M1-43`). Подключается через `-r` (requirements), не `-c`
# (constraints): хэш, заданный в constraints-файле, НЕ прикрепляется к
# требованию и не защищает его под `--require-hashes` — проверено
# прогоном (`pip install -r <версии-без-хэшей> -c <этот-файл>
# --require-hashes` даёт "Hashes are required ... but they are missing",
# хотя хэш присутствует в файле, подключённом через `-c`). Этот файл —
# единственный источник правды о версиях и хэшах зависимостей backend;
# `constraints.txt` (`T-M1-43`) этой задачей упразднён, а не оставлен
# рядом.
#
# Устанавливается ДВУМЯ шагами, не одним — режим `--require-hashes`
# отвергает редактируемую (`-e .`) И обычную установку локального
# каталога одинаково ("Can't verify hashes for these file:// requirements
# because they point to directories" / "...no single file to hash"),
# проверено прогоном для обоих случаев:
#   1) `pip install -r requirements.lock --require-hashes` — все
#      зависимости, с проверкой хэшей;
#   2) `pip install --no-deps -e .` (или `-e ".[dev]"`) — сам проект,
#      ВНЕ режима хэшей (локальный каталог хэшу не подлежит), без
#      повторного разрешения уже установленных зависимостей.
# При такой форме `-e .` в dev-контейнере сохраняется (правки
# `backend/app` подхватываются без переустановки — `T-M1-55`, текст
# задачи до этой правки предполагал иначе, проверено прогоном и
# исправлено).
#
# Сгенерирован внутри одноразового контейнера `--platform linux/amd64`
# (`pip-tools==7.4.1`, `pip-compile --extra dev --strip-extras
# --generate-hashes`), тем же образом и по той же причине, что и прежний
# `constraints.txt` (см. `LOCK_BASE_IMAGE` в корневом `Makefile`): у части
# пакетов состав зависимостей платформенно-условный, а CI и прод —
# linux/amd64.
#
# Главный риск этой схемы для dev-контейнера на arm64 (macOS) —
# `pip-compile`, разрешая граф на amd64, мог бы записать хэши только
# amd64-колёс и ничего не оставить для arm64-колеса той же версии,
# заставляя установку на arm64 упасть жёстко. Проверено прогоном
# (12.10.2026): `pip-compile --generate-hashes` записывает хэши ВСЕХ
# файлов релиза, опубликованных на PyPI для разрешённой версии — sdist и
# КАЖДОЕ колесо под любую платформу, а не только то, которое было
# скачано при разрешении на amd64. Установка этого же, сгенерированного
# на amd64, файла нативно на arm64 (без `--platform`) прошла полностью:
# все 62 дистрибутива, 0 отказов, 0 пропущенных хэшей, без пересборки из
# sdist. Это свойство ТЕКУЩЕГО графа (каждый пакет публикует колесо под
# обе архитектуры или universal-колесо) — не гарантия механизма: пакет,
# публикующий колесо только под одну платформу (без альтернативы и без
# sdist), остался бы недоступен на другой архитектуре НЕЗАВИСИМО от
# хэшей, тем же образом, что и до этой задачи. `--require-hashes`
# дополнительно закрывает пробел, который называл прежний заголовок
# `constraints.txt`: там, где раньше молчаливый пропуск транзитивной
# зависимости был теоретически возможен и не пойман ни одной проверкой,
# теперь pip сам отказывается ставить что-либо, для чего в этом файле
# нет хэша — полнота замка обеспечена МЕХАНИЗМОМ, а не отдельным тестом.
#
# Перегенерировать: `make lock-backend` (тот же одноразовый amd64-
# контейнер, результат не зависит от архитектуры машины, на которой
# запущена команда). Обновление версий — ОТДЕЛЬНЫЙ коммит, не попутно с
# функциональной правкой.
