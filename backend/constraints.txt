# PR #171 review: НЕ точка установки. До T-M1-55 этот файл подключался
# через `-c` во всех трёх точках установки backend; T-M1-55 перевёл их
# на `requirements.lock` (`-r`, с хэшами) и этот файл был удалён как
# неиспользуемый. Он вернулся с ДРУГОЙ ролью: версионный пол для
# `pip-compile -c constraints.txt` внутри `make lock-backend`, и больше
# нигде не упоминается и не ставится. Причина возврата — измерено
# прогоном (PR #171 review): без него перегенерация `requirements.lock`
# (та же команда, без изменений в `pyproject.toml`) подняла версии
# девяти транзитивных пакетов относительно того, что было закреплено на
# момент T-M1-43 (`amqp`, `billiard`, `click-repl`, `httptools`,
# `iniconfig`, `pycparser`, `pydantic`, `pydantic-core`, `wcwidth`) —
# T-M1-43 прямо требует «обновление версий — отдельным коммитом», а
# T-M1-55 добавляет хэши, не версии. `-c` — тот же флаг, что раньше
# использовался для установки, но здесь он передаётся ТОЛЬКО
# `pip-compile` при генерации: ограничивает версию уже разрешённого
# пакета, не запрашивает установку сам — ровно то свойство, из-за
# которого `-c` не годится для реальной установки под `--require-hashes`
# (хэш из `-c`-файла не прикрепляется к требованию, см. заголовок
# `requirements.lock`), но годится для того, чтобы зафиксировать точку,
# от которой `pip-compile` не должен уходить сам.
#
# Версии здесь — снимок `T-M1-43` (04.10.2026, PR #162), без изменений.
# Поднять их осознанно — отдельная задача, `T-M1-57` (ссылка на это
# измерение); такой коммит правит ЭТОТ файл, затем перегенерирует
# `requirements.lock` той же командой `make lock-backend`.
#
# Перегенерировать `requirements.lock` от этого пола: `make lock-backend`.
# Если версия пакета здесь стала невосстановимой (релиз отозван с PyPI
# и т. п.) — `pip-compile` откажет по этому конкретному имени; снять

# рядом с записью, не молчанием.
