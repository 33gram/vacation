# Система учёта отпусков — инструкции для AI-агентов

Проект разрабатывается по подходу Spec-Driven Development. Спецификация написана **до** кода и является обязательной.

## Источник истины

| Документ | Содержание |
|---|---|
| `docs/requirements.md` | Требования с критериями приёмки в нотации EARS. **Единственный источник истины** по тому, что система должна делать. |
| `docs/plan.md` | Архитектура, стек, модель данных, состав API, этапы M0–M8. |
| `docs/tasks.md` | Задачи `T-Mx-yy` — единственный источник истины по их составу и статусу (зеркало в GitHub Issues упразднено, `T-M1-50`). Связь задачи с работой прослеживается по ID в заголовках коммитов (`git log --grep T-Mx-yy`) и в описании PR. |
| `CONTEXT.md` | Доменный словарь и ключевые правила предметной области. |

## Правила работы

1. **Код пишется под задачи из `docs/tasks.md`.** Ветка заводится на связный объём работ — одну задачу `T-Mx-yy` или группу задач с жёсткими зависимостями между собой (например, в M1 24 такие задачи; ветка на каждую по отдельности даёт PR, которые не проходят CI поодиночке). ID всех задач, вошедших в ветку, перечисляются в описании PR; в сообщениях коммитов — ID задачи, к которой относится конкретный коммит. Правки по итогам ревью, а не из `docs/tasks.md`, вместо ID задачи ссылаются на PR и номера замечаний. Заголовок — на английском (см. «Соглашения»), в одной из двух форм: `PR #12 review: <что сделано>` — круг правок по отчёту скила `code-review`; `PR #12 check: <что сделано>` — круг правок по замечаниям проверяющего до запуска ревью. В обеих формах номера замечаний перечисляются в теле коммита, по одному на пункт списка правок, и тело называет источник круга (отчёт ревью или проверяющий). Если правка по итогам ревью порождает новую задачу, она заводится в `docs/tasks.md` отдельным коммитом и дальше цитируется своим ID, а не своим происхождением. Коммит, который не реализует задачу напрямую, но без которого она невыполнима, несёт ID разблокируемой задачи — так же, как коммиты с её кодом; перечень таких случаев закрыт — версия рантайма, конфигурация сборки или CI, замена или фиксация зависимости, — всё остальное является обычным коммитом задачи. Проверяется по дифу: такой коммит не задевает `backend/app/**` и `frontend/src/**` — если для разблокировки приходится менять код приложения, это не разблокировка, и коммит подчиняется общему правилу выше. Отдельная задача под такой коммит не заводится, если работа исчерпывается самой разблокировкой; если по ходу выясняется, что работы больше, она заводится задачей по действующему правилу и дальше цитируется своим ID. Коммит, который меняет только состояние чек-бокса задачи в `docs/tasks.md`, тоже несёт ID этой задачи и может находиться в любой ветке — но только если собственная ветка задачи (та, где задача была реализована, в том числе общая ветка группы задач с жёсткими зависимостями) уже смержена; по умолчанию отметка по-прежнему ставится в собственной ветке задачи. Предусловие проверяется по двум признакам: коммит называет в своём теле PR, которым смержена собственная ветка задачи (иначе факт слияния не виден из дифа и никем не проверяется), и его диф затрагивает ровно один файл, `docs/tasks.md`, где изменены только строки «Версия документа», «Дата» и строка самой задачи с переходом `[ ]`→`[x]` — строки «Основание» и «Статус» такой коммит не трогает. Если хотя бы одно из этих условий не выполнено, коммит подчиняется общему правилу выше. Такая отметка не делает задачу «вошедшей в ветку»: список задач в описании PR перечисляет то, что ветка реализует, и ID отмечаемой задачи в этот список не добавляется.
2. **Критерии приёмки берутся из требований**, а не придумываются: каждый `WHEN`/`IF`/`WHILE`/`WHERE` соответствующего `FR-XXX` становится отдельным тест-кейсом.
3. **Требования не переписываются по ходу реализации.** Если выясняется, что требование неверное, неполное или противоречивое — остановиться, сообщить об этом, изменить `docs/requirements.md` отдельным коммитом с повышением версии документа, и только затем писать код.
4. **Не создавать параллельные спецификации.** Функциональность MVP уже специфицирована: скиллы `to-spec`, `to-tickets`, `grill-with-docs` к ней не применяются. Их место — планирование новых фич после MVP.
5. **Бизнес-правила не хардкодятся.** Значения из раздела 5 требований (28 дней, 14 дней, 2 недели, сроки эскалации) живут в таблице `business_rules_config` и настраиваются через интерфейс администратора (`FR-ADMIN-004`, `NFR-MAINT-001`).
6. **Чек-бокс `[x]` в `docs/tasks.md` ставится только тогда, когда выполнены ВСЕ критерии приёмки задачи.** Частично выполненная задача остаётся неотмеченной; отложенная часть выносится отдельной задачей со ссылкой на блокирующую зависимость (пример — `T-M1-08`/`T-M1-30`).
7. **Работа ведётся скиллами, а не свободным исполнением.** Скилл запускает разработчик — `implement` для задачи из `docs/tasks.md`, `tdd` для тестов из EARS-критериев, `code-review` для ревью в отдельной сессии (см. раздел «Ревью»); сам агент их вызвать не может. Если разработчик не запустил нужный скилл, агент сообщает об этом явно, а не работает в обход молча.
8. **Утверждение в комментарии, докстринге или README проверяется так же, как код.** Текст не описывает гарантию шире, чем показала проверка: если механизм закрывает не все случаи, ограничение называется прямо. Заявление «защищает от любого X» требует либо проверки на всех путях X, либо сужения формулировки. Утверждения о поведении внешних инструментов (pytest, docker, alembic) подтверждаются прогоном, а не рассуждением.
9. **В одном рабочем каталоге в каждый момент ведётся одна ветка — на всё время сессии агента по задаче, а не только на момент вызова инструмента.** Параллельная работа — только через отдельное рабочее дерево (`git worktree add`), где у каждой сессии свой `HEAD`; переключать ветки, делать `reset` или разрешать конфликты в каталоге, где в это время работает агент, запрещено. Причина — потеря незакоммиченных правок в одном из рабочих каталогов, известная по свидетельству работавшего там агента: `reflog` показывает движение ссылок, но не то, был ли `reset --hard` (правило 8 — и про этот файл тоже); подробности — PR #152. Конфликт `docs/tasks.md`, попавший в `main` в том же эпизоде, — отдельный случай небрежного разрешения при мерже, а не следствие двух веток в одном каталоге, этим правилом не закрывается и решается отдельно — `T-M1-51`.

## Ревью

Проект ведёт один разработчик с AI-агентами: ревью выполняет агент, человеческое одобрение PR не требуется и в настройках ветки не включается.

Порядок перед слиянием в `main`:

1. **Pull Request открывается сразу после первого коммита ветки, черновиком, если работа не закончена.** Правка по замечанию, сделанному до появления PR, не может сослаться на его номер, и правило 1 «Правил работы» оказывается невыполнимым не по вине автора. Отчёт ревью кладётся в него комментарием, а правки по итогам ссылаются на его номер (раздел «Правила работы», правило 1).
2. Прогнать скилл `code-review` по двум осям — стандарты кода и соответствие спецификации (`FR-XXX` из `docs/requirements.md`).
3. **Ревью запускается в отдельной сессии агента, а не в той, где писался код.** Агент, проверяющий собственную работу в том же контексте, склонен её защищать, а не искать в ней дыры.
4. Отчёт ревью приложить комментарием к PR — он заменяет подпись человека-ревьюера и остаётся в истории.
5. Каждое замечание либо устранено, либо явно принято с обоснованием в том же комментарии.
6. Зелёный CI обязателен и не заменяется мнением агента: тесты и линтер — объективный критерий, ревью — суждение.

Разработчик читает диффы выборочно, но обязательно в критичных местах: аутентификация и разграничение доступа (`FR-AUTH-*`, `NFR-SEC-*`), расчёт остатков отпуска (`FR-BAL-*`), работа с персональными данными и больничными. Автоматическое ревью здесь дополняет человека, а не заменяет его.

## Скиллы

Установлены в `.claude/skills/` (набор [mattpocock/skills](https://github.com/mattpocock/skills), версии зафиксированы в `skills-lock.json`).

Рабочая связка для MVP:

- `implement` / `implement-spec` — исполнение задачи из `docs/tasks.md`;
- `tdd` — тесты из EARS-критериев требования;
- `code-review` — ревью по двум осям: стандарты кода и соответствие спецификации (`FR-XXX`);
- `diagnosing-bugs`, `codebase-design`, `domain-modeling`, `research`, `triage`, `wayfinder` — по ситуации.

Добавить недостающий скилл: `npx skills@latest add mattpocock/skills -a claude-code --copy -s <имя>`. Скилл-роутер `ask-matt` знает про все 37 скиллов репозитория, включая не установленные здесь.

Скиллы — сторонние инструкции, исполняемые с правами агента. Перед первым применением скилл стоит прочитать.

## Стек

Backend — Python 3.12 + FastAPI + SQLAlchemy 2.x (async) + Alembic, PostgreSQL 16, Celery + Redis.
Frontend — React 18 + TypeScript + Vite + Ant Design.
Инфраструктура — Docker Compose, Nginx, развёртывание on-premise на серверах компании.
Обоснование и детали — `docs/plan.md`, раздел 1.

Каркас проекта (`backend/`, `frontend/`, `infra/`) создаётся задачами этапа M0 — до их выполнения в репозитории только документация и конфигурация.

## Тестирование

pytest (+ httpx) для backend, Vitest + React Testing Library для frontend, Playwright для сквозных сценариев, Locust для нагрузочного тестирования. Тестовый LDAP — OpenLDAP в `docker-compose`, не боевой каталог компании. Подробнее — `docs/plan.md`, раздел 11.

## Соглашения

- Язык документации и доменных терминов — русский; идентификаторы в коде, имена таблиц и полей — английские (соответствие терминов — в `CONTEXT.md`).
- Заголовок коммита — на английском, тело можно на русском.
- Коды отказов в API: **409** — запрос конфликтует с уже записанными данными (дубль уникального значения, существующие события мешают правке); **400** — запрос недопустим сам по себе (смена неизменяемого поля, нарушение бизнес-правила, не связанное с конкретными записями). Ответ-конфликт по полю несёт тот же машиночитаемый префикс поля в тексте (`personnel_number:`, `email:`), что и прежний 400, — поле определяется по префиксу `detail`, а не по коду статуса. Отказ, который нарушает несколько полей сразу, называет все: `<поле>: текст` через `"; "` (`RuleValuesInvalidError`, `MainLeaveTypeProtectedError`); один префикс — частный случай той же записи, разбор на клиенте один (`prefixedMessages`).
- Frontend: каждый голый импорт в `frontend/src` объявлен в `frontend/package.json`; файлы приложения импортируют только из `dependencies`, тесты - из `dependencies` или `devDependencies`; объявленная в `dependencies` зависимость стоит в `package-lock.json` одной копией. Проверяет тест `frontend/src/app/dependencyDeclarationGuard.test.ts` (`T-M2-35`), а не линтер; что считается тестом, область и чего тест не видит - точные границы в его докстринге, здесь перечня нет, чтобы он не разошёлся.
- Персональные данные сотрудников, содержимое `.env`, пароли и параметры LDAP не попадают в код, Issues, PR и логи (`NFR-SEC-001/002/004`).
